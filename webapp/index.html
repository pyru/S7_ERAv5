Spectral Byte Embeddings

Kronecker V2. One substitution — swap the one-hot position axis for a bank of waves — answers both of the problems I picked, because they turn out to be the same problem.

Problem 4

“What is a REAL Fourier alternative of Kronecker? Why can't I represent each character like a Fourier wave, and just add them to make a word?”

Problem 5

“Kronecker is forward deterministic. How do I make a reverse of this? Then we can get rid of the final head, and have a vocab of 1M without any issues.”

§1

The substitution

Kronecker builds a token's code from two one-hot vectors. Spectral Byte Embedding keeps the skeleton and makes the position axis a wave. 

Kronecker   kappa(w) = (1/√L) Σp  onehot256(bytep)  ⊗  onehot32(p)

Spectral    S(w)     = (1/√L) Σp  phi(bytep)      ⊗  psi(p)

            psi(p) = [ .. cos(ωk p), sin(ωk p) .. ]

A one-hot basis is maximally sharp and maximally inflexible: you need one column per position you want to represent, so the number of columns is the maximum token length. Thirty-two columns, thirty-two bytes, hard wall.

A wave basis is a function of p, not a table of rows, so there is no row to run out of. Below the window the two codes carry identical information — psi is an orthogonal change of basis on the very same grid. Above it they part company completely.

§2

Truncation destroys. Folding adds.

This is the whole argument, and you can watch it happen. Each byte of the word is placed at its angle on a 32-position dial. Byte 32 lands back at the top.

Under Kronecker every byte past the window is multiplied by zero — struck through above. Under the spectral codec it folds onto p mod N and adds. Truncation is the special case of a fold whose out-of-window term was replaced by zero, so folding strictly dominates: it never discards anything truncation keeps, and it keeps things truncation discards.

That matters because the two failure modes have different relationships to language. Two tokens collide under truncation whenever they share a 32-byte prefix — and a shared prefix is not a rare accident, it is what morphology is. Under folding a collision needs a numerical coincidence.

A word, and the same word with a comma
Both are real entries in the corpus vocabulary. Under the shipped codec a model cannot learn that one of them ends a clause — the two inputs are the same vector.
§3

Running it backwards deletes the head

Because the position basis is an orthonormal real-DFT frame, the inverse is a matched filter: one fixed tensor contraction, no parameters. 

charlogits[p, b]  =  < code , phi(b) ⊗ psi(p) >

pred_code  = h @ W        # W is the input projection, transposed
charlogits = fixed_inverse(pred_code)
loss       = cross_entropy over the target token's BYTES

No d_model × |V| matrix appears anywhere in the graph. The only trainable tensor facing the vocabulary is W, shaped code_dim × d_model — and |V| does not appear in that shape. In the trained model below the head holds exactly one parameter: a scalar temperature.

With an invertible codec, weight tying stops being a heuristic that trades geometry for memory and becomes exact — the head is WT, because the input and output live in the same space by construction.

§4

What was measured

A real 16 MB multilingual Wikipedia corpus — hi 4.0, ta 3.5, bn 3.0, te 2.1, kn 1.9, en 1.2, mr 0.2 MB — and real byte-level BPE tokenizers trained on it. Nothing below is synthetic.

4.1  The window is a sovereignty bug

Whether 32 bytes is generous depends entirely on which script you write in. UTF-8 spends one byte per Latin character and three per Indic character, and a Devanagari conjunct costs nine.

Result

At the same 8192-dimensional budget the spectral codec collides on zero words where Kronecker collides on 16 673 (6.99 %). Kronecker needs double the budget to get down to 48.

Negative result, reported as found

Over the actual BPE vocabularies the same census found zero collisions for every codec at every vocabulary size. BPE tokens are short — BPE stops merging when frequency runs out. So the strong form of the Session 7 §8 claim is not supported on this corpus.

Two things keep that from settling it. The trend is monotone and points the right way — the longest token runs 16 → 25 → 40 bytes as the vocabulary goes 8 k → 32 k → 131 k, and a 16 MB corpus only produced ~85 k real merges at the 131 072 setting, so this proxy understates a production corpus. And word level is where a byte codec earns its keep anyway: its advertised benefit is that unseen strings still get a sensible vector, and unseen strings are words.

4.2  Fidelity, noise, and the rank bottleneck

Three separate questions, easily conflated. Does the code stay distinct (what an embedding needs)? Does it stay resolvable position by position (what generation needs)? And does it survive being squeezed through d_model (what decides whether any of this is buildable)?

4.3  Does a head-free model learn language?

Five arms, identical trunk, identical data, identical seed, so every adjacent pair isolates exactly one variable.

4.4  Can the head actually go? A prediction, then the test

§4.3 leaves the central claim unsettled: the head-free model works, but it costs real quality at d_model 256. The rank curve says that is exactly the width at which the code cannot fit through the model, which turns into a prediction — recorded before the run, in the experiment's own docstring.

Prediction, registered before running

The head-free penalty shrinks monotonically with d_model, and it shrinks in step with the rank curve — which reads 0.62 at 256, 0.89 at 512 and 0.98 at 768. If the penalty is flat in d_model instead, the rank bottleneck is not the cause and the head-free design is simply worse.

Both arms are retrained at every width, and every arm is now scored two ways. The factorised score is the one §4.3 used: an upper bound, because a byte-factorised model leaks probability onto strings that are not tokens. The exact score renormalises over the vocabulary, which is the distribution the dense head is scored under, so the two finally become the same measurement. That normaliser costs O(|V|) — but only for scoring: training stays O(code_dim) and so does generation.

4.5  A vocabulary of one million

The code is a pure function of a token's bytes, so the |V| × code_dim table is a convenience, never a requirement. Above a threshold the implementation computes codes on demand for the few thousand distinct tokens in the batch and never materialises the table — which is what makes a million-token vocabulary cost what a 32 k one costs.

§5

What the ladder taught me

The frequency ladder is the design, not a detail.

  • A geometric / RoPE-style ladder is broken here. It is the obvious first guess, and ω = π makes sin(πp) = 0 for every integer p — a dead channel — while the slow channels cannot separate adjacent positions. Measured condition number 3.3e17.
  • A plain DFT ladder is exactly orthonormal (condition number 1.000), exactly invertible in-window, and collision-free. It is the default.
  • A multi-modulus “vernier” ladder buys range and costs exactness. On random bytes it decodes 80 positions from 32 channels — real super-resolution by a Chinese-remainder argument. On real text it degrades, because UTF-8 repeats continuation bytes heavily and breaks the sparsity its recovery assumes. At 64 channels it still beats Kronecker-64 on long words with zero collisions.
§6

Honest limitations

  • The likelihood is byte-factorised. It ignores correlations between bytes inside a token and puts mass on strings that are not tokens, so the reported bits-per-byte is an upper bound. A trie-constrained renormalisation would make it exact; it is not implemented.
  • Training is a proxy. CPU-only, a few million parameters, ~1 M tokens. The arms are matched in data, seed and trunk, so the ordering is meaningful; the absolute numbers are not.
  • The corpus is 16 MB — enough for a real multilingual BPE and a real word census, not enough to reproduce production token lengths at V=131 072.
  • Past the grid, resolvability is gone, not just degraded. Folding preserves distinctness, which is what the embedding needs. It does not preserve position-by-position recovery, which is what generation needs.
  • The rank bottleneck is real. At V5's reference shape (code 8 192, d_model 8 096) the ratio is ≈1.01 and it essentially vanishes; in the toy it is 8–32×, so the toy is a pessimistic proxy.
